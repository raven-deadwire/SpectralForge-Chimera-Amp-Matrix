# Independent full-product processor host

This extension is based on PR #103 at
`8c502f4f924886cd036c8367bc32fa6d123f59bd`. It reuses `CallbackRecorder.h`,
`performance.py`, their schemas and the production `ChimeraAmpMatrix` static
target. No parallel DSP implementation, shipping callback hook, publisher or
release-approval engine is added.

PR #93 was inspected at `153f1a6a0400ad38287bbd59030e06dd794fb5cb`.
Its `issue97_gate.py` requires non-synthetic installed-package/DAW evidence.
These results remain **synthetic** and are not converted into its acceptance
reports. Integration means applying this additive target to a future integrated
candidate and rebuilding/repeating; old binary results do not transfer.

## Build and run

Use the repository's normal CMake prerequisites (JUCE 8.0.8, C++20, Python).
The option is OFF by default. Use a fresh build directory and configure again
after changing Git HEAD; source files are watched for reconfiguration.

```sh
cmake -S . -B build-perf -DCMAKE_BUILD_TYPE=Release -DCHIMERA_BUILD_PERFORMANCE_HOST=ON
cmake --build build-perf --config Release --target ChimeraFullGraphHost
```

The executable is under `build-perf/ChimeraFullGraphHost_artefacts/Release/`
(with `.exe` on Windows). All paths passed to the host must be absolute.
Use an explicitly saved Chimera binary state, or author a reproducible **test
fixture** with the host (mode 0/1/2, transpose 0/-2, Dual crossover 0/1):

```sh
ChimeraFullGraphHost --make-state /absolute/classic.chimera 0 0 0
python Tools/SystemPerformance/run_full_graph.py \
  --host /absolute/ChimeraFullGraphHost \
  --source-inputs /absolute/build-perf/full-graph-source-inputs.txt \
  --input /absolute/permission-cleared-48k-DI.wav \
  --state /absolute/classic.chimera --ir /absolute/common-ir.wav \
  --instances 4 --block 128 --seconds 60 --warmup 10 \
  --out /absolute/new-run-directory
python Tools/SystemPerformance/performance.py validate /absolute/new-run-directory/study.json
```

The destination must not exist. Failures retain their raw evidence. Repeated
observations require new destinations; repeat at least three times and alternate
order before drawing comparative conclusions. `--seconds 3 --warmup 1` is useful
for an integration smoke only, and its run ID explicitly retains that duration.

## Scope and evidence

- Runs at 48 kHz, 128/256 frames, 4x. Closed editor, analyzer defaults off.
  GUI/analyzer-open and recording scenarios are not implemented.
- Each active track owns a real processor, prepared before capture. The callback
  scope includes input distribution, **all** processors and averaged stereo
  summing. Their internal PRE/amp/CAB/EQ/POST stages follow the saved state.
  Bypassed effects in that state stay bypassed.
- The explicit workload replaces the A capture in every active CAB lane with
  the supplied common IR, clears modeled B and uses B mix zero. This is not a
  claim to reproduce arbitrary personal IR banks or all cabinet microphone
  combinations. Resolved per-instance states are exported and hashed.
- Input is preloaded and loops without a crossfade. Nonfinite/silent inputs,
  muted amp/CAB lanes, incompatible settings, expired processing, changing
  parameters, missing callbacks, silent instance output or dropped rows fail.
  Each instance's callback count and output energy are retained.
- The binary SHA-256 is computed from the running executable and checked against
  the Python-launched file. Git HEAD **and** a source-content fingerprint are
  embedded; the actual source inventory is copied into each result. The host is
  a separately linked executable, not a hash-equivalent release plugin module.
  Preserve CMakeCache, compiler/JUCE versions and generated lifecycle metadata
  with build evidence. Dirty source is distinguished by the content fingerprint.
- `callbacks.csv` uses the original recorder contract; `study.json` imports it
  through the existing `measure`/`validate` functions and content-addressed raw
  storage. `host.json`, resolved states, controls and a supplemental hash
  inventory stay beside it. `results.md` is generated by the original table tool.
- A handshake starts same-process RSS collection after warmup. RSS is sampled
  every 250ms by Python, outside the callback. It includes the host, all
  processors, workers, preloaded input and telemetry storage, not plugin-only RAM.
- Fixed-epoch pacing preserves late wakeups and scheduled misses; ordinary OS
  sleep and normal priority do not simulate an audio driver. Callback wall load
  and callback-thread CPU load are different. Worker CPU is excluded.
  Windows `GetThreadTimes` is coarse: zero rows and quantized peaks must not be
  interpreted as zero cost or sub-millisecond CPU precision.
- Buffers, processor nodes, MIDI storage and trace rows are allocated before
  callbacks. The executable intercepts ordinary/aligned/array/nothrow C++ new
  on the callback thread, self-tests the probe and fails on retained-callback
  allocations. This does not intercept C malloc/realloc, OS allocation or workers
  and does not certify the product's complete real-time safety.
- 10,000 empty-graph and clock-only callbacks from the **same executable** retain
  recorder/fan-out/fan-in overhead. `overhead.json` recalculates them using the
  existing Python function. These unpaced controls are diagnostic, not a paired
  causal estimate of cache/scheduler effects. Nothing is subtracted from product
  timings and no hardware acceptance threshold is invented.

## Still separate

Real DAW/installed plugin formats, physical interfaces/drivers, xruns, audible
glitches, editor interaction, 30-minute continuous playback and independent
30-minute recording, recorded-file verification and session reopening require
their own observations. Their unknown counters remain null/NOT_RUN.
`requirements_certified=false` and `publication_allowed=false` are unconditional.
No CPU/RAM candidate is promoted to an official specification by this host.
