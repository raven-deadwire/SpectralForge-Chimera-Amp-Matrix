# macOS CAB deadline investigation: source audit

## Scope and status

This audit concerns the deployed source `7b20cd9d1f90e3e2969c250712b199e893cf50cd` and its [CAB realtime run 38175545597](https://github.com/raven-deadwire/SpectralForge-Chimera-Amp-Matrix/actions/runs/38175545597). The earlier comparison is [run 38173348216](https://github.com/raven-deadwire/SpectralForge-Chimera-Amp-Matrix/actions/runs/38173348216). The findings below distinguish source facts, observations from the original callback CSVs, and hypotheses. No product code was changed during this audit.

JUCE references are fixed to commit `d6181bde38d858c283c3b7bf699ce6340c050b5d` (8.0.8). Scheduling-control results belong to the accompanying experiment report; this source audit does not substitute for those measurements. The published beta and its original evidence remain the baseline.

## Established facts

### What the original measurement exercises

The [frozen integration test](https://github.com/raven-deadwire/SpectralForge-Chimera-Amp-Matrix/blob/7b20cd9d1f90e3e2969c250712b199e893cf50cd/Tests/OriginalCabIntegrationTests.cpp) is a console program. Each measured interval calls three independent `Cab::process` instances sequentially, each with two microphones and a 50/50 blend. These are CAB paths with independent lane inputs; they are not actual Classic/Dual/Matrix processor routes or a host/device callback.

The first 1,200 callbacks run with the IR worker; model requests change during the first 80. A `juce::Thread::sleep(1)` request follows each callback for which `n % 8 == 0`. After convergence and fade draining, `library.stop()` joins the worker. Six separately constructed kernels containing copies of one common generated response are then published before a further 400 measured callbacks. The worker is therefore absent from that forced-publication phase. The existing p99 gate and individual wall-deadline records cover all 1,600 measured callbacks per configuration.

The forced phase's microphone configuration requires a separate description. The [initial settings and automation](https://github.com/raven-deadwire/SpectralForge-Chimera-Amp-Matrix/blob/7b20cd9d1f90e3e2969c250712b199e893cf50cd/Tests/OriginalCabIntegrationTests.cpp#L114-L132) distinguish microphone A and B by unit, microphone and distance settings, and change A's position and B's distance. At [line 168](https://github.com/raven-deadwire/SpectralForge-Chimera-Amp-Matrix/blob/7b20cd9d1f90e3e2969c250712b199e893cf50cd/Tests/OriginalCabIntegrationTests.cpp#L168), the forced replacement is derived only from A: `a.position=.85; nextKey=modelKey(a)`, followed by one `wave` generation. The [six-slot loop](https://github.com/raven-deadwire/SpectralForge-Chimera-Amp-Matrix/blob/7b20cd9d1f90e3e2969c250712b199e893cf50cd/Tests/OriginalCabIntegrationTests.cpp#L180-L182) copies that same wave into each new kernel and assigns `nextKey` to every slot, including all three B slots. The [final assertion](https://github.com/raven-deadwire/SpectralForge-Chimera-Amp-Matrix/blob/7b20cd9d1f90e3e2969c250712b199e893cf50cd/Tests/OriginalCabIntegrationTests.cpp#L200-L201) requires all six active model keys to converge to it.

Consequently, the prior A/B response distinctions remain in outgoing or awaiting-swap kernels during the serialized transition. After both microphone fades complete, six independent processing paths use the same replacement response within that configuration. The forced steady portion does not exercise six distinct unit/distance responses. Separate kernel instances and per-slot convolution/filter history remain; common model identity does not imply identical runtime state or prove identical fade ordering across repetitions. [Cab's swap and fade code](https://github.com/raven-deadwire/SpectralForge-Chimera-Amp-Matrix/blob/7b20cd9d1f90e3e2969c250712b199e893cf50cd/Source/Cabinet.h#L160-L214) retains the six steady plus at most three fading path bound throughout this transition.

The test does not create the plugin processor, AU/VST3 wrapper, editor, graphical EQ, tuner, audio device, or actual routing crossover. GUI and full-plugin behavior cannot be assigned as causes of the recorded misses. The [production callback](https://github.com/raven-deadwire/SpectralForge-Chimera-Amp-Matrix/blob/7b20cd9d1f90e3e2969c250712b199e893cf50cd/Source/PluginProcessor.cpp) and [routing engine](https://github.com/raven-deadwire/SpectralForge-Chimera-Amp-Matrix/blob/7b20cd9d1f90e3e2969c250712b199e893cf50cd/Source/ChimeraDSP.h) require separate host-level assessment.

### Scheduling and JUCE

Both original macOS runs report caller base QoS 17, which is UTILITY, and worker JUCE priority `low`. The pinned [JUCE 8.0.8 macOS thread implementation](https://github.com/juce-framework/JUCE/blob/d6181bde38d858c283c3b7bf699ce6340c050b5d/modules/juce_core/native/juce_Threads_mac.mm) maps `Thread::Priority::low` to `QOS_CLASS_UTILITY`. Thus, the console caller and IR worker have the same reported base QoS. These observations do not identify temporary boosts, processor migration, host activity, or a DAW's audio scheduling policy.

The [frozen CMake configuration](https://github.com/raven-deadwire/SpectralForge-Chimera-Amp-Matrix/blob/7b20cd9d1f90e3e2969c250712b199e893cf50cd/CMakeLists.txt) pins JUCE 8.0.8. Its [DSP module](https://github.com/juce-framework/JUCE/blob/d6181bde38d858c283c3b7bf699ce6340c050b5d/modules/juce_dsp/juce_dsp.cpp) enables vDSP on Apple platforms by default. The [Apple FFT implementation](https://github.com/juce-framework/JUCE/blob/d6181bde38d858c283c3b7bf699ce6340c050b5d/modules/juce_dsp/frequency/juce_FFT.cpp) uses per-instance FFT setup and `vDSP_fft_zop`/`vDSP_fft_zrip`. It contains no JUCE processing spinlock. The fallback FFT's spinlock belongs to a different backend and is not an established explanation for this Apple path. Static inspection does not prove anything about undisclosed synchronization inside Accelerate.

The broader JUCE processing paths are distinct. [JUCE convolution](https://github.com/juce-framework/JUCE/blob/d6181bde38d858c283c3b7bf699ce6340c050b5d/modules/juce_dsp/frequency/juce_Convolution.cpp) has a background engine queue and a try-locked pending-engine transfer; factory/user IRs and unsupported custom-kernel configurations can take this fallback. It is not the convolution loader exercised by these modeled timing configurations. [VST3](https://github.com/juce-framework/JUCE/blob/d6181bde38d858c283c3b7bf699ce6340c050b5d/modules/juce_audio_plugin_client/juce_audio_plugin_client_VST3.cpp) and [AU](https://github.com/juce-framework/JUCE/blob/d6181bde38d858c283c3b7bf699ce6340c050b5d/modules/juce_audio_plugin_client/juce_audio_plugin_client_AU_1.mm) wrappers acquire the processor callback lock. [Parameter notification](https://github.com/juce-framework/JUCE/blob/d6181bde38d858c283c3b7bf699ce6340c050b5d/modules/juce_audio_processors/processors/juce_AudioProcessor.cpp) also acquires a listener lock; production MIDI controller handling can call it. Those paths were assessed as full-plugin concerns, not as causes present in the CAB-only measurement. This audit makes no blanket claim that the complete plugin or JUCE is lock-free.


### Ownership, allocation, and convolution work

The measured configurations select the custom [ModeledCabConvolution](https://github.com/raven-deadwire/SpectralForge-Chimera-Amp-Matrix/blob/7b20cd9d1f90e3e2969c250712b199e893cf50cd/Source/ModeledCabConvolution.h) path through [Cab::Kernel](https://github.com/raven-deadwire/SpectralForge-Chimera-Amp-Matrix/blob/7b20cd9d1f90e3e2969c250712b199e893cf50cd/Source/Cabinet.h), rather than JUCE's asynchronous convolution loader.

Response generation, FFT setup, spectra and buffer allocation happen during preparation or [IRLibrary worker builds](https://github.com/raven-deadwire/SpectralForge-Chimera-Amp-Matrix/blob/7b20cd9d1f90e3e2969c250712b199e893cf50cd/Source/IRLibrary.cpp). The callback exchanges raw kernel pointers and retires old kernels; the worker collects and destroys them. Shared ownership of prepared responses is not acquired/released by callback processing. No explicit callback allocation, IRLibrary mutex acquisition, kernel destruction, or loader join was found in the measured custom route. The test's C++ `new/delete` guard remains narrower than a universal malloc, lock, or fault tracer.

Fixed-size callbacks use a uniform partition schedule, without an occasional large tail FFT. All model generations emit the same `ceil(sampleRate * 0.085)` response length: [original v1](https://github.com/raven-deadwire/SpectralForge-Chimera-Amp-Matrix/blob/7b20cd9d1f90e3e2969c250712b199e893cf50cd/Source/OriginalCabModel.h), [expanded v2](https://github.com/raven-deadwire/SpectralForge-Chimera-Amp-Matrix/blob/7b20cd9d1f90e3e2969c250712b199e893cf50cd/Source/CabExpansionModel.h), and [array v3](https://github.com/raven-deadwire/SpectralForge-Chimera-Amp-Matrix/blob/7b20cd9d1f90e3e2969c250712b199e893cf50cd/Source/CabLayoutModel.h). At a fixed rate, buffer and channel count, their runtime FFT and partition geometry is therefore identical. Six physical speaker units increase model-generation work; six speaker simulations do not run in each callback.

## Observations requiring controlled follow-up

- Among worker-phase wall misses whose paired CPU also exceeded the budget, **8 of 20** latest observations and **11 of 24** earlier observations have `callback_index % 8 == 1`: the first callback after the explicit sleep request. Only one eighth of that phase's callback positions have this residue. This is a wakeup association, not proof of a scheduling cause.
- None of the latest 25 CPU-over wall misses occurs at callback 0 or 1,200. The five forced-phase CPU-over observations occur at phase indices 97, 125, 131, 132 and 167. At 96 kHz/64 samples, index 167 follows completion of both serialized 50 ms fades. An initial-publication or fade-only explanation is insufficient.
- Some paired CPU spikes are isolated by two orders of magnitude. Original-v1/96 kHz/64/mono callbacks 424, 425 and 426 respectively record approximately 19.5, 4,237.6 and 36.7 microseconds CPU. The source does not schedule comparably different arithmetic at those positions.
- Latest CPU-over wall misses occur in v1/v2, with none in array v3. Because their partition geometry is equal, that distribution does not establish intrinsically higher callback complexity in v1/v2.

**CPU-envelope caution:** [CabTimingDiagnostics](https://github.com/raven-deadwire/SpectralForge-Chimera-Amp-Matrix/blob/7b20cd9d1f90e3e2969c250712b199e893cf50cd/Tests/CabTimingDiagnostics.h) reads the thread clock before and after the wall interval. Paired CPU includes a different measurement envelope and is not exact DSP-only CPU time. Latest expanded integration/96 kHz/64/mono callback 1,102 has approximately 1,031.5 microseconds CPU but 626.4 microseconds wall. Neither paired CPU-over nor wall-minus-CPU should be treated as an exclusive attribution to DSP execution or descheduling.

## Hypotheses and disposition

Scheduling/wakeup effects, memory faults/cache disturbance, and intermittent convolution-stage CPU cost remain hypotheses. Spectral multiply-accumulate is the dominant steady-state stage in the separate instrumented profile, but that profile does not pair a stage's CPU time with the original misses. Failed ARM vectorization has not been demonstrated.

JUCE's [ScopedNoDenormals implementation](https://github.com/juce-framework/JUCE/blob/d6181bde38d858c283c3b7bf699ce6340c050b5d/modules/juce_audio_basics/buffers/juce_FloatVectorOperations.cpp) sets ARM FPCR FZ bit 24. The test has one guard around its matrix and production has one per `processBlock`; no recorded FPCR observation proves a denormal problem. GUI FFT and tuner work occur outside this CAB test. They should be investigated only in an additional full-plugin experiment, using the [graphical EQ DSP](https://github.com/raven-deadwire/SpectralForge-Chimera-Amp-Matrix/blob/7b20cd9d1f90e3e2969c250712b199e893cf50cd/Source/GraphicalEQ.h), [message-thread FFT](https://github.com/raven-deadwire/SpectralForge-Chimera-Amp-Matrix/blob/7b20cd9d1f90e3e2969c250712b199e893cf50cd/Source/GraphicalEQPanel.h), and [tuner worker](https://github.com/raven-deadwire/SpectralForge-Chimera-Amp-Matrix/blob/7b20cd9d1f90e3e2969c250712b199e893cf50cd/Source/GlobalDSP.h) as distinct factors.

**No product fix is yet justified by this audit.** Preserve the frozen acceptance conditions, full callback population and all misses. An experimental caller-QoS change is diagnostic context, not a plugin improvement. A worker-priority or spectral-loop change requires its own controlled comparison, with response fidelity, fade behavior, model readiness and unchanged acceptance gates retained. Nothing here justifies shortening IRs, reducing units/paths, raising buffer sizes, or suppressing failure records.


## Independent next experiments if QoS results remain mixed

A mixed ABBA result is not a basis for changing the production callback's scheduling policy. A sentinel miss demonstrates that a timing anomaly can occur without CAB processing; a clean sentinel does not clear CAB. Its much shorter arithmetic workload and elapsed exposure prevent subtraction of sentinel time or direct equivalence of miss counts.

The following are additional research experiments. They must use separate diagnostic executables or conditions, preserve their full observations, and leave the original 66-configuration acceptance matrix intact.

| Experiment | Controlled comparison and required evidence | What it can decide |
|---|---|---|
| Attribute the CPU spikes | At the recorded 96 kHz/32 and /64 configurations, capture the same interval's per-stage wall/CPU evidence, active/fading path counts, swap/reset flags, and FPCR FZ state. Capture system scheduling/fault traces in a separate instrumented run. Repeat with the instrumentation absent. | Whether a spike is associated with a particular DSP stage, wakeup, reset, fault, or measurement overhead. An attributed stage remains a finding to reproduce, not an automatic fix. |
| Separate caller QoS from pacing | Keep source, compiler, lane/mic configuration and callback population fixed. Independently vary inherited/user-interactive caller QoS and the test's sleep placement in a diagnostic factorial comparison; repeat and counterbalance order on more than one runner allocation. | Whether the existing wake association depends on caller context, pacing, or runner allocation. These changed conditions do not replace acceptance. |
| Isolate worker interference | Use pregenerated kernels and the same deterministic publication schedule in worker-present and worker-absent research arms. Log actual model generations and fade counts, including kernel request-to-ready time where relevant. | Whether response preparation causes additional interference when publication/DSP work is held comparable. Worker effects cannot account by themselves for the original misses after `library.stop()`. |
| Check memory behavior | Supplement the existing C++ operator guard with native allocation and page-fault evidence at the same callback boundaries; include cold publication and suspended-mic wake separately from steady processing. | Whether allocation, page residency, or large history clearing is actually implicated. Do not infer universal allocation freedom from the existing guard. |
| Test a minimal spectral-loop candidate | Inspect the exact AppleClang vectorization report/assembly first. If it reveals a concrete problem, compare one loop change against the frozen implementation with repeated order-balanced runs and the independent impulse/FIR/channel-isolation oracles. Keep every IR sample, partition, fade and deadline threshold. | Whether an arithmetic change improves reproducible callback cost without altering response or transferring the failure elsewhere. |
| Reproduce in a native host | Measure an actual AU/VST3 or CoreAudio callback at the affected settings, recording caller policy and whole-callback timing. Compare editor closed/open, FFT display off/on, tuner off/on and MIDI/routing automation one factor at a time; include actual smaller/variable blocks under a larger prepared capacity. | Whether a real host reproduces the issue and whether wrapper, GUI, notification or reset paths add a separate cause. Console results alone do not establish DAW glitch behavior. |

Only a modification with a reproduced cause, a favorable independent control, preserved numerical behavior, and unchanged acceptance checks should enter a later product-performance PR. Diagnostic completion or a more favorable individual run does not meet that standard.
