# Transpose 후보 고정 PDC 계약 준비 — 2026-10-25 KST

T6 항목 중 **고정 PDC 계약**을 준비한 문서다. 대상은 T6 시험 후보 `corr40-split-v3`다.

**결론:**

- **계약안:** 보고 지연 L = **2.5ms**로 정했다. 반음과 관계없이 하나의 값이고, 표본률마다 샘플 수만 다르다.
- **사전 등록한 새 시드 검증:** 48·96kHz는 통과, 44.1kHz는 실패했다.
- **44.1kHz 실패 원인:** 아주 약한 마커가 섞인 입력 하나다. 그 입력은 v2에서도 같은 값이 나오고, 어택 지표 자체가 불안정한 경계 사례다.
- **연구용 플러그인:** 고정 PDC 모드와 '보고 지연만큼 지연되는 바이패스'를 넣었다. 호스트 점검 144회가 모두 통과했다.

제품 `Source/`와 연구 엔진 코드는 바꾸지 않았다. 측정은 합성 입력만 썼다.

## 왜 고정 PDC가 문제인가

**제품 엔진.** 제품 엔진(`PolyPitch`)은 FFT 창 길이를 지연으로 보고한다(44.1/48kHz 2048샘플, 96kHz 4096샘플). DAW는 그만큼 트랙을 앞당겨 맞춘다.

**후보 엔진.** 후보는 읽기 지연이 음마다 2–40ms 사이에서 변한다. 어떤 고정값을 보고해도 정확히 맞출 수는 없다. 그래서 계약은 다음 두 부분으로 정의했다.

1. **보고값 L:** 고정값이다. 반음이나 엔진 상태로 바뀌지 않고, 표본률이 바뀔 때만 샘플 수가 다시 계산된다.
2. **잔차 한계:** DAW가 L만큼 보정한 뒤 남는 오차(= 실제 추가 지연 − L)의 한계다.
   - 어택(1–8kHz)에만 둔다.
   - 저역 onset은 L로 보정되지 않는다(아래 표). 그래서 따로 보고한다.

## L을 정한 방법 (기존 시드)

**도구:** `Tools/TransposeNext/pdc_study.py`. v3로 렌더해 이벤트마다 다음 두 가지를 쟀다.

- 어택 peak 추가 지연(T1 지표)
- 저역 무게중심 추가 지연(T2/T3 지표)

**유효 기준:** T1과 같다. 입력 자체의 어택 peak가 모두 이벤트 뒤 10ms 안에 있는 입력만 썼다.

**L 결정 규칙:** 0.25ms 간격 후보 중 '어택 잔차 절댓값의 최댓값'이 가장 작은 값이다.

| 표본률 | 어택 이벤트 | 어택 추가 지연 (최소 / 중앙 / 최대) | 규칙이 고른 L | L 보정 후 잔차 최대 | 0 보고 시 잔차 최대 |
|---|---:|---|---|---:|---:|
| 44.1kHz | 1,912 | −0.23 / 3.04 / 5.40ms | 2.5ms (110샘플) | 2.90ms | 5.40ms |
| 48kHz | 1,912 | −0.38 / 3.03 / 5.58ms | 2.5ms (120샘플) | 3.08ms | 5.58ms |
| 96kHz | 1,912 | −0.39 / 3.02 / 5.55ms | 2.5ms (240샘플) | 3.05ms | 5.55ms |

세 표본률 모두 2.5ms가 나와서 이 값 하나로 정했다. 반음별 어택 추가 지연 범위는 다음과 같다.

| 반음 | 어택 추가 지연 |
|---|---|
| −2 | −0.1–3.2ms |
| −1 | −0.1–2.8ms |
| +1 | −0.2–3.9ms |
| +2 | −0.4–5.6ms |

**저역 onset 추가 지연.** 3.4–17.9ms다(+2반음 B0/A0 긴 음이 가장 길다). L 보정 뒤에도 저역 onset은 어택보다 0.9–15.4ms 늦다.

## 사전 등록한 새 시드 검증

**사전 등록:** 렌더 전에 커밋 `063d292`로 push했다.

- **새 시드:** holdout 26457/31623/36056, 긴 음 2236
- **고정한 것:** L = 2.5ms, 렌더러(`549e475`)
- **기준:** 표본률마다 '어택 잔차 절댓값 최대 ≤ 4.5ms'. 기존 시드 최댓값 3.08ms + 1ms를 0.5ms 단위로 올림한 값이다(T3 상한과 같은 방식).

| 표본률 | 어택 이벤트 | 잔차 최대 (기준 4.5ms) | 잔차 p5 / p95 | 0 보고 시 최대 | 저역 잔차 (보정 안 됨) |
|---|---:|---|---|---:|---|
| 44.1kHz | 2,488 | **53.24ms → FAIL** | −0.12 / 2.58ms | 55.74ms | 0.9–14.2ms |
| 48kHz | 2,424 | **2.92ms → PASS** | −0.13 / 2.58ms | 5.42ms | 0.2–14.5ms |
| 96kHz | 2,424 | **2.91ms → PASS** | −0.19 / 2.54ms | 5.41ms | 0.9–13.7ms |

### 44.1kHz 실패 분석

기준을 넘은 16개 이벤트가 **모두 한 입력**에서 나왔다. 기타 A1, 지속음 위 무작위 약한 마커(시드 26457), 44.1kHz다.

- **입력이 경계 사례다.**
  - 44.1kHz에서는 입력 자체의 어택 peak가 7.0ms 뒤에 있어 유효 기준(10ms)을 통과했다.
  - 같은 입력이 48kHz에서는 45ms여서 판정에서 빠졌다.
  - 마커(진폭 0.001–0.008)가 지속음의 고역보다 약해서, 어택 지표 자체가 불안정하다.
- **다운시프트 음수 값(최대 −6.3ms):** 입력 쪽 peak가 지속음에 걸려 생긴 것으로 보인다.
- **업시프트 큰 값(+1반음 55.7ms, +2반음 38.1ms):** 예전 rt에서 본 T1 실패와 같은 모양이다. 고역 접합 잡음이 약한 마커보다 커서 어택 peak로 잡힌 것으로 보인다.
- **v2도 같다:** 이 입력의 업시프트 결과는 v2와 v3가 완전히 같다(44.1kHz +1 55.74ms, +2 38.05ms).
- **결론:** v3나 L 선택 때문이 아니다. 이 입력은 T1으로 봐도 v2·v3 모두 실패하는 새 사례다.

**처리.** 규칙대로 44.1kHz 판정은 FAIL로 기록하고, 결과를 본 뒤 L·지표·기준을 바꾸지 않는다. 남은 일은 두 가지다.

1. **업시프트 고역 접합 잡음:** 약한 마커 위에서 다시 생기는 원인을 분석한다.
2. **어택 지표 검토:** 약한 마커 입력에서 지표가 불안정한 문제를 본다. 지표를 바꾸려면 근거를 먼저 문서화한다.

**후속 분석 (`TRANSPOSE_ATTACK_METRIC_FAINT_MARKERS_20261025.md`):** 이 입력의 마커는 1–8kHz 배경보다 0–6dB밖에 높지 않다. 기준을 넘은 이벤트는 모두 SNR 6dB 미만이었다. 이벤트별 SNR ≥ 10dB 기준을 다음 사전 등록 검증부터 적용하자고 제안했다. 지난 판정은 바꾸지 않는다.

**SNR ≥ 10dB 기준 재검증 (`TRANSPOSE_PDC_SNR10_FRESH_SEED_20261026.md`):** 새 시드 41421/44721/48990(긴 음 3317)에서 사전 등록한 기준으로 세 표본률 모두 통과했다. 잔차 최대는 3.03 / 2.79 / 2.96ms다.

이 입력을 빼면 44.1kHz 잔차 최대는 기존 시드와 같은 범위(≈3ms)다. 이 값은 참고일 뿐 판정에 쓰지 않는다.

## 연구용 플러그인 구현

**파라미터.** `Latency report`: Live (0) / Fixed PDC. 기본값은 Live다.

| 모드 | 보고하는 지연 |
|---|---|
| Live | 0. 직접 모니터링용이고, 출력은 원음보다 약 2–6ms(어택 기준) 늦게 들린다 |
| Fixed PDC | round(2.5ms × 표본률) = 110 / 120 / 240샘플 |
| 제품 엔진 | 모드와 관계없이 FFT 창 길이 |

**바이패스.** 호스트 바이패스 때 원음을 보고 지연만큼 지연시킨다(`processBlockBypassed`). 처리 중에도 지연선을 채워 두어, 바이패스로 바꾸는 순간에도 이어진다. 이전에는 JUCE 기본 동작이라 지연 없이 원음이 나가서, 2048샘플을 보고하는 제품 엔진도 바이패스 때 트랙 위치가 어긋났다.

**호스트 점검 (144회 = 3 표본률 × 6 입력 × 엔진 2 × 반음 4).** 항목 9개가 모두 통과했다.

- 기존 6개: 고정 블록, 지연 보고, 가변 블록, 재준비, 상태 복원, 자동화
- 새로 넣은 3개:
  - 고정 PDC 보고값: v3 110/120/240샘플, 제품 2048/4096샘플
  - 모드를 바꿔도 출력 비트 동일
  - 바이패스 지연 = 보고 지연

큰 블록 차이도 0/216이었다.

## 계약안 요약 (연구 단계)

1. **보고 지연:** L = round(2.5ms × 표본률). 반음·엔진 상태로 바뀌지 않는다. Live 모드는 0이다.
2. **어택 잔차:** DAW 보정 후 |실제 어택 지연 − L| ≤ 4.5ms를 목표로 한다. 합성 새 시드에서는 48·96kHz 충족, 44.1kHz 미충족(위 경계 사례)이다.
3. **저역 onset:** L로 보정되지 않는다. 보정 후에도 0.2–15.4ms 늦다. 이 한계는 문서로 공개한다.
4. **바이패스:** 보고 지연과 같은 만큼 지연된다.
5. **남은 확인:** 실제 DAW에서의 PDC 동작(점검표 D04/D05), 실제 DI에서의 잔차. 44.1kHz 경계 사례는 분석을 마쳤고, SNR ≥ 10dB 기준 재검증에서 세 표본률 모두 통과했다.
