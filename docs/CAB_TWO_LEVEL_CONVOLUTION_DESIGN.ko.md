# CAB 2단계 분할 컨볼루션 — 설계 검토와 프로토타입 결과 (2026-11-03)

상태: **프로토타입 / 제품 미적용.** 이 문서와 `Tests/prototypes/`의 코드는 제품 빌드,
CTest, 배포 패키지에 포함되지 않는다. 결론은 **현재 형태로는 제품 적용을 권하지 않는다**이다
(아래 "판단").

## 1. 배경

macOS CI의 `ChimeraCabExtendedTimingTests`가 간헐 실패한다(최근 8일 27회 중 2회:
#231 `98b172a`, #253 `3624acc`, 재실행 시 통과). 로컬 Linux(4 vCPU Xeon 2.8 GHz VM)에서도
6회 중 1회 재현됐다. 실패 지점은 항상 **96 kHz · 32샘플 · 스테레오, 캐비닛 3 × 마이크 6**이며,
기준은 콜백 wall-time p99 < 블록 주기(333 µs)다. 기준·예산은 이 작업에서 바꾸지 않았다.

### 현재 비용 구조 (stage profile, 3회)

`ChimeraCabProfiling --expanded --extended-buffers`, 96 kHz/32/stereo, 콜백 1개(마이크 6개) 기준:

| 단계 | p50 | 비중 |
|---|---|---|
| spectral MAC | 70–77 µs | ~60% |
| FFT 정·역 | 37–41 µs | ~30% |
| 필터 등 | ~8 µs | ~7% |
| 콜백 전체 p50 / p99 | 124–132 / 266–325 µs | 예산 333 µs |

모델 응답은 `ceil(rate × 0.085)` = 8,160샘플(96 kHz). 현재 엔진(`ModeledCabConvolution`)은
JUCE와 같은 균일 분할을 쓰며 B=32에서는 FFT 128, 분할 96샘플 → **86개 분할**을 매 블록
곱·누적한다. 마이크당 블록마다 약 170 KB의 스펙트럼을 읽는다. 비용은 대략
`응답 길이 × 마이크 수 / 블록`에 비례하므로 이 설정이 가장 빡빡하다.

### 측정 스레드 우선순위 변경(A안)은 효과 없음

측정 콜백을 실시간 스레드(SCHED_RR 99, 로그로 확인)에서 돌려도 6회 중 1회 실패했다
(wall p99 491 µs, thread-CPU p99 495 µs). 스케줄러 선점만의 문제가 아니라 CPU 비용 자체가
예산을 넘는 경우가 있다. 이 변경은 push하지 않았다.

## 2. 설계안: 2단계 분할 (head + tail)

```
y = head * x + tail * x
head : 응답의 앞 H 샘플. 기존 ModeledCabConvolution 그대로, 오디오 스레드, 지연 0.
tail : 나머지를 K 샘플 분할(2K FFT)로, 공유 작업 스레드가 한 K 블록 뒤에서 계산.
```

- tail 블록 m(입력 [mK, (m+1)K))은 출력 시각 mK + H부터 기여한다. 입력은 (m+1)K에
  완성되므로 **H = 2K이면 작업 스레드에 K 샘플의 시간**이 주어진다. 추가 지연은 없다.
- 스테레오는 제품과 같이 left + i·right 복소 스트림 하나로 처리한다.
- 오디오 스레드는 샘플마다 입력 링에 쓰고 출력 링에서 읽은 뒤 지우며, K 샘플마다
  세마포로 작업 스레드를 깨운다. 작업 스레드는 acquire/release 원자 카운터로 완료 블록을
  공개한다. 늦으면 해당 샘플은 head만 출력하고 `late_samples`로 센다.
- B=32에서 head(H=1024)는 11개 분할로 줄어든다(86 → 11).

프로토타입 파일:
- `Tests/prototypes/CabTwoLevelConvolution.h` — 엔진(head는 제품 클래스 재사용)
- `Tests/prototypes/CabTwoLevelBenchmark.cpp` — 비교 벤치마크
- CMake 대상 `ChimeraCabTwoLevelPrototype` (`EXCLUDE_FROM_ALL`, CTest 없음)

벤치마크 조건: 85 ms 합성 응답(지수 감쇠 잡음) 6개, 스테레오, 1,600 콜백을 **실시간 간격으로
페이싱**(작업 스레드 마감이 실시간이므로), 입력 잡음 동일. 정확도는 같은 입력 1초에 대해
현재 엔진 출력과, 그리고 double 정밀도 직접 컨볼루션과 비교한다. 실행 기계는 위 로컬 VM.
실제 CAB 테스트의 필터·크로스페이드·IR 생성 작업은 포함하지 않으므로 절대값은 CAB
테스트보다 작다.

## 3. 결과

원본 로그: `docs/verification/cab-two-level-20261103/`.

### 정확도 — 목표 충족

모든 실행·설정에서 상대 최대 오차: 현재 엔진 대비 **1.7e-7 – 3.7e-7**, 직접 컨볼루션 대비
**1.7e-7 – 3.0e-7**(float 반올림 수준). 늦은 샘플이 없는 경우에 한한다.

### 오디오 스레드 비용 — 핵심 설정에서 소폭 개선

96 kHz · 32샘플 (K = 512, 3회):

| 실행 | 현재 p50 / CPU p99 | 2단계 p50 / CPU p99 | late 샘플 |
|---|---|---|---|
| 1 | 84.8 / 166.5 µs | 60.4 / 128.2 µs | 0 |
| 2 | 81.0 / 199.0 µs | 79.2 / 140.2 µs | **4,544** |
| 3 | 89.3 / 174.3 µs | 73.7 / 144.2 µs | 0 |

- CPU p99는 **약 17–30% 감소**. 기대했던 "수 배"에는 못 미친다. MAC은 줄지만 FFT 2회(마이크당
  128점)는 그대로이고, 샘플 단위 링 처리 비용이 더해진다.
- 다른 설정은 개선·악화가 섞인다. 44.1/48 kHz의 128·256샘플에서는 2단계가 더 느린 경우가
  있다(예: 48 kHz/128 p50 233 → 299 µs).

### 작업 스레드 마감 — 신뢰성 문제

| K (마감 @96 kHz) | 늦은 샘플이 생긴 설정 |
|---|---|
| 128 (1.3 ms) | 9개 중 7개 |
| 256 (2.7 ms) | 12개 중 5개 |
| 512 (5.3 ms) | 3회 중 2회에서 발생 (96k/32, 96k/256) |
| 1024 (10.7 ms) | 1회 실행에서 1개 (48k/256). 96k/32 CPU p99는 205 → 143 µs로 여전히 감소했지만, 44.1/48 kHz의 64–256샘플 6개 중 4개는 p50이 더 느렸다 |

작업 스레드는 일반 우선순위 `std::thread`였다. 늦은 샘플은 **응답 꼬리가 빠진 출력**,
즉 들리는 오류다. 공유 VM에서 수 ms의 마감도 보장되지 않았다.

## 4. 판단

**현재 형태로는 제품 적용을 권하지 않는다.**

1. 핵심 설정의 이득(CPU p99 약 20–30%)은 실패를 줄일 수는 있지만, 이 설정을 넉넉하게
   만들 만큼 크지 않다(CAB 테스트 기준 p99 266–325 µs → 추정 200–260 µs).
2. 두 번째 실시간 마감을 만든다. 작업 스레드가 늦으면 소리가 틀린다. 현재 엔진에는 이런
   실패 모드가 없다. 이를 막으려면 작업 스레드 실시간 우선순위(플랫폼별 권한), 호스트
   스레드 수 제한, 오프라인 렌더(호스트가 실시간보다 빠르게 처리) 시 동기 처리 전환,
   지연 시 정책(무음/앞 블록 재사용/동기 계산)이 모두 필요하며 각각 별도 검증 대상이다.
3. 일부 설정은 더 느려진다.

이 결론은 로컬 Linux VM 1대의 측정에 근거한다. macOS·Windows 실제 기기, 실시간 우선순위
작업 스레드, 실제 CAB 경로(필터·크로스페이드 포함)는 측정하지 않았다.

## 5. 대안과 다음 단계 (결정 필요)

| 안 | 내용 | 예상 효과 | 비용·위험 |
|---|---|---|---|
| a. head 경로 미세 최적화 | MAC 메모리 배치(입력 스펙트럼 3배 링 → 캐시 친화 배치), 블록 내 샘플 처리 벡터화 | 미측정 | 제품 코드 변경, 정확도 회귀 시험 필요 |
| b. 응답 길이 제한 (높은 샘플레이트) | 85 ms 꼬리 일부 절단 | 길이에 비례 | 음색 변화, 청취 승인 필요 |
| c. 지원 범위 명시 | 96 kHz·32샘플·3캡·6마이크를 보장 범위 밖/경고로 | 코드 없음 | 기준 완화 성격, 소유자 결정 |
| d. 2단계 계속 | 실시간 작업 스레드 + 지연 정책 설계 후 실제 기기 측정 | 위 20–30% 이상은 불확실 | 위 §4-2 전체 |
| e. 현 상태 유지 | 간헐 실패 시 해당 작업 재실행 | — | CI 잡음 지속(~7%) |

권장: **e를 유지하면서 a의 효과를 먼저 측정**한다. a는 지연·스레드 구조를 바꾸지 않아 위험이
작다. b·c는 음색과 제품 범위에 관한 결정이다.

## 재현

```
cmake --build build --target ChimeraCabTwoLevelPrototype
build/ChimeraCabTwoLevelPrototype_artefacts/Release/"Chimera CAB Two-Level Prototype" 1600 512
#   인자: 콜백 수, tail 분할 K (head = 2K). 종료 코드 1 = 정확도 실패 또는 late 샘플 존재.
cmake --build build --target ChimeraCabProfiling
build/ChimeraCabProfiling_artefacts/Release/* --expanded --extended-buffers   # 현재 엔진 단계별 비용
```

6회는 `601d4ce`(main `0b247dc` + EQ 편집 커밋, CAB 코드 동일)에서 측정.
