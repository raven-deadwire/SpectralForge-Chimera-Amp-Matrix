# OBS 사용자 IR 복원 검토 — 2026-11-02

검토 대상: PR #251, `9a382a593d66a4866bfa9002da1c37c803b8d4ce`.
이 문서의 원본 CI 결과는 해당 커밋에만 적용한다. 아래 후속 수정의 실제 OBS 실행 결과로 승계하지 않는다.

## 판정

정상 IR의 장면 저장·재시작 복원, 단순 Base64 형식 오류의 필터 대체,
인스턴스 해제 시험은 실제 제품 경로를 거친다. 다만 손상된 길이 접두부는
기존 시험에 없었고, 실제 `IRLibrary::restore()`에서 예외를 재현했다.
후속 수정과 새 OBS 회귀 시험이 통과하기 전에는 손상 IR 안전성 검증 완료로 판단하지 않는다.

## JUCE 계약과 기존 리뷰

제품이 고정한 JUCE 8.0.8 (`d6181bde38d858c283c3b7bf699ce6340c050b5d`)의
`modules/juce_core/memory/juce_MemoryBlock.cpp`를 대조하고 실제 모듈을 컴파일했다.

- 문자 수는 `((size * 8) + 5) / 6`. PR의 수정 계산이 정확하다.
- 빈 블록은 `0.`이다. 빈 문자열로 바꾸라는 기존 리뷰는 틀리며 수정하지 않았다.
- 과거 인코더의 추가 점 문자는 디코딩 시 선언된 크기 밖의 비트가 버려져 원본 바이트를 바꾸지 않는다.
- Python 인코더와 JUCE의 실제 인코더를 빈 입력, 0–511바이트 입력, 전체 바이트 값, 실제 시험 WAV를 포함한 515개 입력으로 비교했다. 전부 일치했다. JUCE의 왕복 및 추가 점 문자 왕복도 통과했다.
- 외부 OBS 상태는 표준 Base64이고 내부 `USER_IRS` 데이터는 JUCE MemoryBlock 형식이다. 두 계약을 혼동하지 않는다.

## 재현 결함과 수정

`fromBase64Encoding()`은 문자열 길이가 아니라 접두부에 적힌 크기로 먼저 메모리를 할당한다.
기존 제품의 6MiB 문자열 제한과 디코딩 이후 4MiB 검사는 이 할당을 막지 못한다.

실제 제품 `IRLibrary.cpp`, 실제 공장 IR 바이트와 JUCE 8.0.8을 연결한 독립 실행 파일에서:

| 저장된 IR 데이터 | 수정 전 | 수정 후 |
|---|---|---|
| `@@ not JUCE base64 @@` | 필터 대체 | 필터 대체 |
| `-1.A` | `std::bad_alloc` 전파, 미처리 실행 파일 SIGABRT | 필터 대체 |
| `2147483647.A` | 256MiB 주소 공간 제한에서 같은 예외 | 필터 대체 |

이는 실제 OBS 프로세스의 크래시 실측이 아니라 OBS가 호출하는 제품 복원 경로의 재현이다.
새 `IRStateEncoding.h`는 할당 전에 십진 크기를 오버플로 없이 검사한다.
동일한 디코더를 사용하는 inline IR 복원과 `IR_ASSETS` 풀 생성·복원에 모두 적용했다.
제품 상태 스키마, 파라미터 ID, 정상 IR 바이트, `0.`, 과거의 추가 점 문자 허용은 유지한다.
유효하지 않은 pooled 자산은 기존 계약대로 상태 전체를 거절하며, inline 손상 IR은 해당 칸을 필터로 대체한다.

## 로컬 회귀 결과

- `ChimeraIRStateEncodingTests`: 258개 정상/추가 점 문자 왕복, 빈 블록, 잘못된 접두부 12종, 4MiB 경계 및 문자열 상한 통과.
- 실제 `ChimeraIRLibraryTests`: 새 손상 복원 7종, 이전 IR 제거, 정상 다른 칸 보존, 필터 출력 일치 통과. 새 회귀는 수정 전 코드에서 `FAIL: std::bad_alloc`로 실패했다.
- 기존 IR 제거·파일 삭제 후 복원·원본 바이트와 메타데이터 보존·worker 취소·warm cache 시험도 통과.
- 실제 `irState::pool()`/`unpack()` 독립 검사: 잘못된 크기 4종 거절, 정상 추가 점 문자 자산 왕복 통과.
- Python 구문 및 inline/pooled 원본 WAV 검사: 통과. 데이터가 빠진 상태를 통과시키지 않음을 확인했다.

로컬 C++ 검사는 g++ C++20과 JUCE 8.0.8 모듈을 직접 연결했다. 전체 플러그인·CMake·실제 OBS 실행을 로컬에서 재실행한 결과는 아니다.

## 후속 OBS 회귀 범위

기존 세 소스에 음수 길이 IR과 유효한 JUCE 인코딩의 손상 WAV를 추가했다.
다섯 소스를 두 번 실행하여 모든 손상 유형의 필터 대체, 10개 인스턴스 해제를 검사한다.
저장·복원 상태에서는 이름 존재뿐 아니라 세 live lane의 원본 WAV 바이트를 검사하고,
재시작 후에는 레벨과 주파수 분포를 함께 비교한다. 새 실제 OBS 결과는 후속 PR의 CI에서 별도로 확인해야 한다.
