# 짧은 오프라인 베타테스터 코드 (소유자용)

## 적용 범위와 현재 상태

발급은 소유자의 별도 도구에서만 합니다. Chimera에는 코드 발급 기능이나 공통 비밀값을 넣지 않고, **미리 승인한 코드의 SHA-256 확인값 목록**만 넣습니다. 서버·로그인·인터넷 연결은 필요하지 않습니다.

코드 형식은 기존과 같은 `CHT1-<NAME>-<CHECK>`이며 마지막 부분은 Crockford Base32 **6자리**입니다. 이름은 영문 대문자·숫자 2–16자입니다. 대소문자, 공백, 확인 문자에서 O·I·L을 0·1로 입력하는 편의 기능은 유지합니다. 문서의 `<NAME>`과 `<CHECK>`는 실제 코드가 아닙니다.

이 변경에 포함된 `Validation/tester-code-allowlist.json`은 **비어 있습니다**. 따라서 기본 빌드는 어떤 테스터 코드도 받지 않습니다. 실제 코드의 발급·기존 코드 이관·공개 확인값 목록 반영·메일 발송·배포는 수행하지 않았고 각각 필요한 승인을 받은 뒤 진행해야 합니다. 기존 메일 초안의 코드는 자동으로 등록되지 않습니다.

승인된 코드가 등록되면 베타 만료를 **무기한** 해제하는 기존 권한을 유지합니다. 이후 모든 베타에서도 그 권한을 유지하려면 승인된 확인값을 다음 빌드에 계속 보존해야 합니다. 이 설계 변경을 이유로 기존 테스터 권한을 임의 축소하지 않습니다. 일반 사용자에게는 버전별 승인 만료일(beta.2: 2027-03-31 23:59 KST)이 그대로 적용됩니다. 만료일 승인과 실제 배포 승인은 별개입니다.

## 1. 소유자 전용 발급 흐름

`Tools/tester_code.py`는 개발 저장소에서 소유자가 실행하는 관리 도구이며 제품 바이너리나 설치 패키지에 포함하지 않습니다. 공통 발급 키를 만들지 않고 암호학적 난수로 코드를 선택합니다.

1. 소유자가 발급 대상 이름과 수량을 정하고 필요한 발급 승인을 확인합니다.
2. 도구는 이름·코드 원문이 있는 비공개 파일을 **Git 작업 디렉터리 밖**에 저장합니다. 기존 파일·심볼릭 링크를 덮어쓰지 않으며 POSIX에서는 처음 쓰는 순간부터 `0600` 권한을 사용합니다. 원문 코드를 기본 stdout·CI 로그·저장소에 출력하지 않습니다. Windows에서는 소유자 전용 ACL을 별도로 확인해야 합니다.
3. 비공개 파일에서 확인값만 담은 공개 manifest를 내보냅니다. manifest는 `schema`와 `digests` 두 필드만 가지며 이름·원문 코드·발급 키를 포함하지 않습니다.
4. 별도로 승인된 공개 manifest를 `Validation/tester-code-allowlist.json`에 반영하고 정확한 소스로 빌드·검증합니다. 제품은 이 목록에 있는 코드만 받습니다.
5. 해당 빌드에서 실제 등록을 확인한 뒤 승인된 수신자에게 코드를 전달합니다. beta.1에는 등록 메뉴가 없으므로 아직 없는 기능을 현재 공개 설치본에서 사용할 수 있다고 안내하지 않습니다.

승인 후 사용하는 명령 형식은 다음과 같습니다. 아래 이름은 설명용 자리표시자이며 이번 변경에서 실행한 발급 내역이 아닙니다.

```sh
python Tools/tester_code.py issue --name TESTER01 --private-out "/개인/경로/tester01.private.json"
python Tools/tester_code.py export --private-file "/개인/경로/tester01.private.json" --out "/검토/경로/tester-code-allowlist.json"
```

여러 비공개 파일의 확인값을 합칠 때 `--private-file`을 반복합니다. 새 목록을 기존 승인 목록 대신 쓸 때 이전 테스터의 확인값을 빠뜨리지 않도록 비교 검토합니다. CLI에는 발급용 서버나 공통 비밀키가 없습니다. 실제 코드는 비공개 파일에서만 확인하고 승인된 테스터에게 전달합니다.

정확한 옵션은 `python Tools/tester_code.py --help`와 각 하위 명령의 `--help`를 사용합니다. 비공개 파일을 이 저장소, 공유 폴더, CI 아티팩트 또는 지원 로그에 올리지 마세요.

### 새 테스터와 여유분

여유분을 미리 만들어 빌드에 포함했다면 **이미 포함된 코드**를 나중에 배정할 때 앱 업데이트가 필요하지 않습니다. 이름도 확인값에 결합되므로 이미 만든 코드의 이름을 나중에 바꾸면 다른 코드가 됩니다. 새 이름·새 코드를 추가하거나 승인 목록을 변경하려면 새 manifest와 새 빌드가 필요합니다. 준비 수량과 대상 이름은 아직 확정하지 않았습니다.

### 기존 짧은 코드 이관

형식 유지가 기존 HMAC 검증 알고리즘 유지를 뜻하지 않습니다. 기존 원문 코드는 소유자가 승인하여 같은 정규화 규칙으로 확인값을 등록한 경우에만 새 빌드에서 사용할 수 있습니다. 앱은 HMAC 비밀값이나 이전 알고리즘으로 임의 이름의 코드를 재계산하지 않습니다. 이번 작업에서 실제 초안 코드를 읽거나 이관하지 않았습니다.

## 2. 확인값과 빌드 경계

확인값은 UTF-8 문자열 `chimera-tester-allowlist-v1|` 뒤에 **정규화된 전체 코드**를 연결한 SHA-256입니다. 이름과 마지막 6자리를 함께 결합하므로 다른 이름으로 옮긴 코드는 통과하지 않습니다. 확인값은 64자리 소문자 16진수입니다.

CMake는 manifest 형식·필드·확인값 길이와 문자·중복을 검사하고 `generated/ChimeraTesterAllowlist.h`를 만듭니다. 잘못된 manifest는 구성 단계에서 실패합니다. 빈 manifest는 정상적으로 빌드되지만 코드 기능은 꺼져 있습니다. GitHub Actions에 `CHIMERA_TESTER_SECRET`을 추가할 필요가 없으며 제품 빌드에서 그 비밀값을 읽지 않습니다.

## 3. 테스터 입력과 오디오 동작

- SETTINGS → **Enter beta tester code...** 에 코드 전체를 붙여넣고 APPLY를 누릅니다.
- 코드는 사용자·컴퓨터별 설정에만 저장하며 프로젝트·프리셋·A/B 상태·참조 파일에는 쓰지 않습니다.
- 이미 열려 있던 다른 창은 **RECHECK CLOCK**을 누르거나 다시 열면 저장 상태를 반영합니다.
- 정상 코드가 있으면 `testerExtended` 상태가 되어 카운트다운·만료 경고가 사라집니다. 잘못된 빌드 메타데이터까지 무시하는 권한은 아닙니다.
- REMOVE가 성공해도 이미 연주 중인 인스턴스의 오디오는 끊지 않습니다. 이후 새 인스턴스에는 원래 만료 정책이 적용됩니다. 삭제 실패는 성공으로 표시하지 않습니다.
- Linux/macOS 코드 파일은 저장·교체 처음부터 `0600`입니다. Windows는 사용자 AppData 디렉터리의 ACL을 상속하며 실제 다른 계정 접근 검사는 배포 전 확인 항목입니다.

## 4. 반드시 이해할 한계

**6자리 확인 문자는 약 30비트뿐입니다.** 공개 확인값을 얻은 공격자는 앱의 시도 제한을 우회해 별도 프로그램에서 가능한 코드를 대입할 수 있습니다. 해시로 바꿔도 짧은 코드의 추측 가능성이 없어지지는 않습니다. 이 방식은 제한된 베타 테스터 관리용이며 강력한 라이선스 보호·위조 방지·DRM이라고 설명하지 않습니다.

- 앱에서 발급용 공통 비밀값을 추출해 무제한 새 이름의 코드를 계산하는 기존 문제는 제거합니다. 그러나 유효 코드를 추측하거나 바이너리 자체를 패치하는 공격까지 막지는 못합니다.
- 정상 코드의 복사·공유는 기존 정책대로 가능하며 이름은 실제 신원이나 기기 소유권의 증명이 아닙니다.
- 오프라인으로 실행하는 구버전에서 즉시 권한을 회수할 수 없습니다. 이후 빌드에서 확인값을 제거하더라도 이미 배포된 바이너리에는 소급되지 않습니다.
- 새 빌드에 승인 목록을 누락하면 기존 코드가 인식되지 않습니다. 이후 베타의 목록 보존·업데이트·재실행·삭제·실제 패키지 검증이 필요합니다.

이전 HMAC 구조의 분석은 [PR #181 보안 검토](PR181_TESTER_SECURITY_REVIEW_20261026.ko.md)에 보존되어 있으며, 해당 문서의 HMAC 비밀값 설명은 이전 구현에 관한 기록입니다.
